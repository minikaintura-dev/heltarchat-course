Module 1: Foundations and Authentication Complete

Goal: Make your first authenticated API call.

Core concepts

  • Base URL: https://api.heltar.com/v1
  • Every success returns message and data. Errors return errorType, errorMessage, errorsValidation, errorRaw.
  • Phone numbers use international format without +, for example 919876543210.
  • Rate limits: list reads 600 per 15 min, analytics 60 per 15 min, key management 20 per 15 min. Sends are not limited this way.

Authentication

  • Create a key under Settings → API Key / Dev tools. The full key is shown only once.
  • Send it as Authorization: Bearer hk_live_…
  • Scopes are resource:action, such as messages:write. A call outside the key's scope returns 403.
  • Presets: Full access and Read-only.
curl -X GET "https://api.heltar.com/v1/clients?limit=5" \
  -H "Authorization: Bearer hk_live_xxxxxxxx"

Module 2: Messaging and Contacts API Complete

Goal: Send every message type and manage contacts programmatically.

Sending messages

  • Supported messageType values: text, media, template, interactive, contacts, location, reaction.
  • Templates are required outside the 24-hour customer service window. Variables map to {{1}}, {{2}} by position.
  • Read data.success and data.fail carefully. Both are keyed by array position, so match results back to what you sent.
  • Use refId to correlate your own IDs.

Media workflow

  1. GET /v1/messages/presigned-url?file_name=…&file_type=…
  2. PUT the file to signedRequest (expires after one hour).
  3. Send the message with the returned url.

Contacts

  • POST /v1/clients creates or upserts in bulk. Attributes merge key by key.
  • Attribute types: text, numerical, dropdown, tags. Define non-text types first with POST /v1/business/attributes.
  • Pagination is keyset-based: pass nextCursor back as cursor until it is null.

Module 3: Campaigns, Templates and Scheduling Complete

Goal: Run bulk campaigns reliably and manage the template lifecycle.

Templates

  • Categories: UTILITY, MARKETING, AUTHENTICATION. Components must include BODY.
  • Statuses: PENDING, APPROVED, REJECTED, PAUSED, DISABLED.
  • Editing replaces the whole component list, and approved templates go back to review.
  • Pause all marketing sends with PUT /v1/business/pause-marketing-templates.

Campaigns

  • Small batches go in messages. Large ones use an NDJSON file, one recipient per line, referenced by finalPayloadFileUrl with recipientCount.
  • Track counts with GET /v1/campaigns/get-one/:id. Per-recipient status is at GET /v1/campaigns/:id.

Scheduling

  • Schedule a message, campaign or nudge with a Unix timestamp no more than two years ahead.
  • Scheduling a nudge cancels pending nudges for the same contact and bot.

Module 4: Webhooks and Real-Time Events Complete

Goal: Receive and process events reliably.

Setup

  • Configure URLs with POST /v1/business/webhook-url. Each URL subscribes to one field type.
  • Use headers to send a static shared secret, since there is no signature header.

Payload discrimination

EventWhere it arrives
Inbound customer messagevalue.messages[]
Status change (sent, delivered, read, failed)value.statuses[]
PaymentStatus with "type": "payment"
Call event"field": "calls"

Reliability rules

  • Respond 200 within 10 seconds. Process asynchronously.
  • Only network errors, timeouts and 5xx are retried, up to 5 times over roughly 4 to 5 hours. Sort by payload timestamps, not arrival time.
  • Deduplicate on (wamid, status).
  • After about 100 consecutive failures the webhook is disabled. Re-enable it with the configure endpoint.

Module 5: Guides in Practice Complete

Goal: Apply the three guides to real workflows.

Custom data in webhooks

  • Attach integrations: [{ name: "metaCustomFieldHook", customField: {...} }] to a template send.
  • The returned customField lets you map every receipt back to your own order ID.

Receiving media

  • Inbound media arrives as an ID. Fetch GET /v1/messages?wamid=….
  • awsLink may be empty for a few seconds. Retry about three times at five-second intervals.

Custom domain for link tracker

  • Use an unused subdomain such as links.yourbrand.com. Never the root domain.
  • Add the verification CNAME exactly as sent. Don't duplicate your domain in the Name field.
  • Set Cloudflare records to DNS only. Keep the verification record forever, because renewal depends on it.

Final Assessment

Try each question first, then open the answer.

1. Why does a 200 response to POST /v1/messages/send not guarantee delivery?

The 200 means the message was accepted. Delivery is reported later through sent, delivered, read and failed status webhooks.

2. What happens after roughly 100 consecutive failed webhook deliveries?

The webhook is disabled automatically and you are notified. Re-enable it with the configure endpoint once your endpoint is healthy.

3. Which field tells you whether a webhook payload is a customer message or a status update?

Look at which array is present: value.messages[] for inbound customer messages, value.statuses[] for status updates.

4. Why must the web widget signature be computed on the server?

The HMAC secret must stay private. If it is computed in the browser, anyone can read it and forge signatures for any visitor id.

5. Why must the Cloudflare verification record be DNS only?

A proxied (orange cloud) record hides the real value, which blocks both certificate verification and the final link setup.
